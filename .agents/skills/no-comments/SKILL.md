# No comments

Spawn Comment Sicko. Act on accepted findings.

Defer to Comment Sicko's fresh perspective.

Rationale belongs in the wiki and invariants belong in tests. A comment cannot fail, so it protects nothing. When a deleted comment carried a real "why", move it to the PR body and the commit message, and to the repo's wiki. If that wiki is generated by a tool, update it through the tool, never by hand, and never point at a generated wiki path from source. A repo's own `AGENTS.md` or `CLAUDE.md` can set a stricter comment rule, such as no code comments at all; read it first, and it wins.

## Scope

Use the caller's files or diff. Otherwise use the current diff against the base branch, default to the resolver's trunk (`node .agents/skills/factory-context/scripts/resolve.mjs --field project.trunk`), including the working tree.

## Steps

1. Spawn a `general-purpose` subagent told to read [`prompts/comment-sicko.md`](prompts/comment-sicko.md) in this skill's directory and act as that persona. Pass the scope. Do not restate its rules.
2. Inspect its report and diff. Reject application-code edits, scope escapes, exception-protected deletions, deleted `CONSTRAINT` comments, misstated `MUST KILL` reasons, and flags that treat kept intentional code as guilty. Reshape flags on our-code surprises stay actionable. Do not restore those comments. A keep survives only with proof it is about something we cannot change. Audit missed scoped lint and TypeScript suppressions. Correctness or safety suppressions stay actionable `MUST KILL`s. Restore deletions only with exact exceptions and scoped proof. Before accepting thin `IMPORTANT` or `do not remove` kills or keeps, trace their symbol yourself: how it works (callers, callees, the runtime path) and why it is shaped that way (`git blame`, `git log -L`, the introducing PR via `gh pr view`, its ticket). If a kill is ambiguous, do not restore. If a keep is refuted or still ambiguous, delete it. Revert and rerun one rejected report with the failure named. Reject a second, report it open, and fail `/no-comments`.
3. Fix trivial accepted flags directly by deleting a dead path, dropping a parameter, or using the real API. If any fix needs a shape, sketch it once for the accepted set and surrounding code: types and signatures with `not implemented` bodies, at least two structurally distinct candidates, and pick the one that hides more behind a smaller interface. Stop at the sketch. Step 4 implements.
4. Implement the smallest root-cause fix in scope: fix the first place the code went wrong, not the place the symptom surfaced, and shape it as if the requirement had been there from the start. Remove every named workaround. If the root cause is out of scope, land the smallest in-scope fix and report the rest open. Neither goal authorizes widening the fence nor fixing instances outside it. Never bolt on symptom guards.
5. Constraint comments say `do not remove`, `do not change wording`, `do not change this to X`, or `talk to X before changing`. Leave keeps about things we cannot change. For the rest, prove the invariant is enforced elsewhere before the comment goes: make the exact change the comment warns against, run the tests, and confirm something goes red. Then revert the change. If something goes red, delete the comment. If nothing does, the comment is the only guard: offer the cheapest in-scope test, type, runtime check, or lint that goes red on that change, and wait for interactive approval. Unattended and eval runs require caller pre-approval. If approved, encode it, prove it goes red on the warned-against change, then delete the comment. Otherwise keep the comment, report the constraint open, and sketch the out-of-scope work.
6. Report the deletion count, restored comments, reruns, the sketch, fixes, encoding offers, encodings with their red-run proof, constraint comments kept unenforced, rationale moved to the wiki or PR body, and other open work.
